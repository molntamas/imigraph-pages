Try it: you choose the order

In the automaton, all blocks of one partition act at once, then all blocks of the other. In the graph nothing says "at once": a rule fits at one square at a time. Here you make the events yourself, one block at a time, in any order you like. A block may act when all four of its cells have its turn; a ring marks it. Click a ring, or any cell of its block.

The number in a cell says how many events the cell has been through. Lean proved that whatever order you choose, every cell holds exactly what the automaton has in that cell after that many steps. The table under the pictures checks it for the world on your screen; the proof is for every world of every even size.

A filled cell holds a particle. The small corner of a cell points at the block whose turn it is. Where four corners meet, the block may act.

What Lean is, in a few sentences

Lean is a programming language in which one can also write down mathematical statements and their proofs. A statement is a line of the language (theorem ...). A proof is a text that a small, carefully kept program, Lean's kernel, checks step by step. If the files build, every theorem in them is proved; a wrong step does not build. Nobody has to trust the author of a proof, human or AI: the kernel is the judge.

What Lean cannot judge is whether a statement says what one meant. A theorem about a table that was typed in wrongly is still a theorem, about the wrong table. So this page rests on two things, and shows both:

In Lean the table is a list and a function that looks a block up in it:

def tableList : List Block := [0, 8, 4, 12, 2, 10, 9, 7, 1, 6, 5, 11, 3, 13, 14, 15]
def table (b : Block) : Block := tableList.getD b.val 0

Statements about the table have finitely many cases, so Lean can simply try them all. Two of them, as they stand in the file:

theorem table_table : ∀ b : Block, table (table b) = b := by decide
theorem table_keeps_particles : ∀ b : Block, particles (table b) = particles b := by decide

A test in Python could check the same 16 cases. The difference shows in the next section, where the cases are not finitely many.

Worlds of every size

In Lean a world is the whole plane: a cell for every row and column. A world that wraps round (a donut) is a plane that repeats, so a theorem about every plane is a theorem about every donut of every size. One step:

abbrev World := Int → Int → Bool
def blockAt (w : World) (r c : Int) : Block :=
  ofCells (w r c) (w r (c + 1)) (w (r + 1) c) (w (r + 1) (c + 1))
def step (p : Int) (w : World) : World := fun r c =>
  cell (table (blockAt w (r - (r - p) % 2) (c - (c - p) % 2)))
    ((r - p) % 2 == 1) ((c - p) % 2 == 1)

Three statements that no test can settle, because they speak of infinitely many worlds:

theorem step_step (p : Int) (w : World) : step p (step p w) = w
theorem particles_conserved (p : Int) (m n k : Nat) (w : World)
    (hw : Periodic (2 * (m : Int)) (2 * (n : Int)) w) :
    tile (run p k w) 0 0 (2 * m) (2 * n) = tile w 0 0 (2 * m) (2 * n)
theorem speed_limit (p : Int) (n : Nat) : ∀ (w w' : World) (r c : Int),
    (∀ r' c', r - n ≤ r' → r' ≤ r + n → c - n ≤ c' → c' ≤ c + n → w r' c' = w' r' c') →
    run p n w r c = run p n w' r c

In plain words: every step undoes itself; a world that wraps round after 2m rows and 2n columns keeps its number of particles through any number of steps; and what happens in a cell after n steps depends only on cells at most n away (the automaton has a speed limit of one cell per step).

One proof, read line by line

The proof that a step undoes itself is seven lines. It leans on facts proved just before it in the same file.

theorem step_step (p : Int) (w : World) : step p (step p w) = w := by
The statement. For every whole number p (which partition acts) and every world w: the step made twice gives w back. After by comes the proof.
funext r c
Two worlds are the same world if they hold the same in every cell. So take any cell: row r, column c.
have hr : (r - (r - p) % 2 - p) % 2 = 0 := by omega
A small fact about even and odd numbers: the top row of this cell's block is a row where blocks start. omega is Lean's own method for such arithmetic; it finds the proof by itself.
have hc : (c - (c - p) % 2 - p) % 2 = 0 := by omega
The same for the column.
show cell (table (blockAt (step p w) _ _)) _ _ = w r c
Write out what the second step does at this cell: it takes the cell's block as the first step left it, looks it up in the table and reads the cell off.
rw [blockAt_step p w _ _ hr hc, table_table]
Rewrite with two facts proved before. blockAt_step: after the first step, that block is the table's entry for the old block. table_table: the table looked up twice gives the block back. What is left to show: the cell's place in its old block holds what the cell held.
exact cell_blockAt p w r c
That is exactly the fact cell_blockAt. Nothing is left to show, and Lean accepts the theorem.

Graphs and rules in Lean

The graph model has no rows, columns or clock: only nodes and arrows. In Lean a graph is a list of arrows, a rule is two small graphs whose nodes are letters, and one application of a rule (an event) is defined in three lines:

abbrev Graph (α : Type) := List (α × α)
structure Rule where
  lhs : Graph Nat
  rhs : Graph Nat
def inst {α : Type} (σ : Nat → α) (pattern : Graph Nat) : Graph α :=
  pattern.map fun a => (σ a.1, σ a.2)
def Rewrites {α : Type} (rule : Rule) (g g' : Graph α) : Prop :=
  ∃ (σ : Nat → α) (rest : Graph α),
    g.Perm (inst σ rule.lhs ++ rest) ∧ g'.Perm (inst σ rule.rhs ++ rest)

Read: graph g rewrites to g' by a rule if there is a choice of nodes for the rule's letters (σ) and a remainder rest such that g is the rule's left side with those nodes plus the remainder, and g' is the right side with the same nodes plus the same remainder. Perm says "the same arrows, in any order". This is the whole meaning of rewriting, for graphs of pairs; an engine is a fast way of finding such choices.

The six rules are not typed in as six lists of arrows. They are built from the table by a function, so that a rule cannot disagree with the table by a slip of the pen:

def triangle (alive : Bool) (acting other mid : Nat) : Graph Nat :=
  if alive then [(acting, other), (mid, acting), (mid, other)]
  else [(acting, other), (acting, mid), (mid, other)]
def side (b : Block) (toward : Bool) : Graph Nat :=
  [(q 0, q 1), (q 1, q 2), (q 2, q 3), (q 3, q 0)]
    ++ (List.range 4).flatMap fun i =>
      if toward then triangle (corner b i) (p i) (q i) (m i)
      else triangle (corner b i) (q i) (p i) (m i)
def ruleOf (b : Block) : Rule := ⟨side b false, side (table b) true⟩
def kinds : List Block := [0, 1, 3, 6, 7, 15]

Every cell has three nodes: a corner on the square of each of its two blocks, and a middle node. A rule takes the square of one block (corners q0 to q3, clockwise from the top left) with the triangles of its four cells (other corner p, middle node m) and puts the same nodes back with some arrows turned round.

The theorem

The graph has no clock. Nothing in it says "now all even blocks, then all odd blocks". A rule fits wherever a square has its four cross arrows leaving it, and whoever applies the rules may take those places in any order: here an even block, there an odd one that is already allowed to, elsewhere nothing yet. So the world the graph stands for is, in general, no world the automaton ever has as a whole. The claim that the graph nevertheless plays the automaton needs saying exactly, and this is how Lean says it:

def worldGraph (rows cols : Nat) (k : Nat × Nat → Nat) (W : World) : Graph (Node (Nat × Nat)) :=
  netGraph (torusCells rows cols) (torusNxt rows cols)
    (fun rc => run 0 (k rc) W (rc.1 : Int) (rc.2 : Int)) (fun rc => k rc % 2 == 1)
theorem graph_plays_automaton (m n : Nat) (hm : 0 < m) (hn : 0 < n) (W : World)
    (hW : Periodic (2 * (m : Int)) (2 * (n : Int)) W) {g : Graph (Node (Nat × Nat))}
    (h : Reaches rules (worldGraph (2 * m) (2 * n) (fun _ => 0) W) g) :
    ∃ k : Nat × Nat → Nat, g.Perm (worldGraph (2 * m) (2 * n) k W)

Read: W is a world that repeats after 2 m rows and 2 n columns. worldGraph ... k W is the graph in which every cell rc holds what the automaton has there after k rc steps (run 0 (k rc) W), and it is the odd block's turn exactly where k rc is odd. With all k zero it is the start graph. The theorem: whatever graph g the six rules reach from the start graph (Reaches rules ... g: any number of events, anywhere, in any order), there are numbers k such that g is that graph. The graph can run ahead in one place and lag in another. It can never show anything the automaton does not compute.

The proof has three parts, each a file of its own. First, a triangle of a cell can be found in the graph in one place only, so a rule's left side can lie only on a real block all of whose cells have its turn (event_is_block; the case analysis is done by Lean's grind). Second, such an event makes of the block what the automaton makes of it, and because the four cells of a block that may act have always been through the same number of events, a world that is on the automaton's history stays on it (Slice.act). Third, on a donut the walk round a block is the automaton's step on the plane (astep_eq_step).

Lean refused one statement. The first version of sources_are_particles said: in the piece of a block, the nodes that nothing points at are its particles. Lean answered that this is false. In the piece of a block that has acted, the four outer corners have no arrow pointing at them either; theirs comes from the square of a neighbouring block, which is not part of the piece. The statement that holds counts middle nodes only. A test with a whole world would not have shown this; the checker did, within seconds.

What is not proved

  • That the graph never gets stuck. Every block whose four cells have its turn can act (proved, for every size), and at the start every even block is such a block. That at every later moment at least one block may act is not proved; on the small worlds Lean computed it, and the tests see it on random runs.
  • That the Lean definitions are the project's. No proof can say this. Tests hold them equal for the table, the six rules (arrow by arrow), the 16 pieces of graph and 30 worlds up to 8 x 8 (18 of them with the events of a step, against the rewriting engine).
  • That the graph named by row and column is the graph numbered by the Python code, for every size. The theorem is about the first; the Python code and its engine use the second. Lean computed that they are the same for every world up to 4 x 4, and the tests compare them up to 8 x 8.
  • What the gas does in the long run (walls that stand still, mixing), and the other rules of the project: not attempted.

Doing this for your own systems

The Lean on this page was written by an AI coding agent in two sessions and checked by Lean after every change. The agent did not need to be trusted: one of its statements was false and a number of its proof steps did not hold, and Lean said so each time. That loop (write, let Lean check, repair) is how AI systems now make progress in mathematics, and it carries over to cellular automata and graph rewriting as it stands. What carries over well:

  • Laws: something is kept (particles, arrows, the graph without directions), something can be undone, something has a speed limit.
  • "The graph plays the automaton", as a statement about all worlds and all orders, not a sample.
  • "A rule fits only where it should": the question every graph model raises, and the one tests answer least well.

What does not: anything that is seen rather than stated (a pattern looks like a glider, a gas mixes), and finite checks on large worlds, where Lean is far slower than ordinary code. Tests stay; Lean adds the statements tests cannot reach.

Lean in physics, in short

  • Physlib (before: HepLean, then PhysLean; kept by the Lean community since 2026) is the shared library of physics in Lean: mechanics, electromagnetism, quantum mechanics, relativity, statistical mechanics and more. github.com/leanprover-community/physlib
  • Lanyon AI (Jonathan Gorard, Ammar Hakim, Jimmy Juno; announced July 2026) generates simulation code for equations of physics together with Lean proofs about it. The generator is not public; generated solvers with their Lean proofs are. github.com/lanyonai
  • Cellular automata in Lean exist for one-dimensional automata and for results on symmetric configurations. No block automaton, lattice gas or Wolfram model in any proof assistant was found when this was written (November 2026).
  • The limit everyone names: a checked proof says nothing about whether the definitions are the physics one meant.
